# Inside TLS 1.3

TLS 1.3 (RFC 8446, 2018) was a redesign. It removed everything that had been attacked in earlier versions: RSA key transport, CBC modes, RC4, SHA-1, renegotiation, compression and custom DH groups. It also completes the handshake in **one round trip**.

## The handshake

```
Client                                              Server
ClientHello
  + supported versions, cipher suites
  + key_share (e.g. X25519MLKEM768, X25519)   ──────►
                                                    ServerHello
                                                      + key_share
                                              ◄──── {EncryptedExtensions}
                                                    {Certificate}
                                                    {CertificateVerify}   signature over the transcript
                                                    {Finished}            MAC over the transcript
{Finished}                                    ──────►
[Application data]                            ◄────► [Application data]
```

`{ }` marks messages encrypted with handshake keys. Everything after the ServerHello is encrypted, **including the server's certificate**, which TLS 1.2 sent in the clear.

## How each primitive is used

| Need | Primitive in TLS 1.3 |
|---|---|
| Key agreement with forward secrecy | ephemeral (EC)DHE only: X25519, P-256, or hybrid X25519MLKEM768 |
| Server authentication | a signature (ECDSA, Ed25519 or RSA-PSS) over the **hash of the whole transcript**, in CertificateVerify |
| Handshake integrity | Finished: HMAC over the transcript, with a key derived from the handshake secret |
| Record protection | AEAD only: AES-128-GCM, AES-256-GCM or ChaCha20-Poly1305 |
| Key derivation | HKDF throughout |

Signing the **transcript** (every handshake message so far) is what defeats the man in the middle: Mallory can't substitute her own key share without breaking the signature. It also defeats **downgrade** attacks, because the list of offered algorithms is part of what's signed.

## The key schedule

TLS 1.3 derives every key from a chain of HKDF steps. With $\operatorname{Derive}(S, \ell, M) = \operatorname{HKDF\text{-}Expand\text{-}Label}(S, \ell, H(M))$:

$$
\begin{aligned}
\text{early} &= \operatorname{HKDF\text{-}Extract}(0,\ \text{PSK or } 0) \\
\text{handshake} &= \operatorname{HKDF\text{-}Extract}\big(\operatorname{Derive}(\text{early}, \texttt{"derived"}, \varepsilon),\ \text{(EC)DHE shared secret}\big) \\
\text{master} &= \operatorname{HKDF\text{-}Extract}\big(\operatorname{Derive}(\text{handshake}, \texttt{"derived"}, \varepsilon),\ 0\big)
\end{aligned}
$$

and from these, using the transcript hash at that point:

$$
\begin{aligned}
\text{client/server handshake traffic} &= \operatorname{Derive}(\text{handshake}, \texttt{"c hs traffic"} / \texttt{"s hs traffic"}, \text{ClientHello..ServerHello}) \\
\text{client/server application traffic} &= \operatorname{Derive}(\text{master}, \texttt{"c ap traffic"} / \texttt{"s ap traffic"}, \text{ClientHello..server Finished})
\end{aligned}
$$

- Separate keys per **direction** and per **phase**, each bound to the transcript.
- Record nonces are a 64-bit **sequence number** XORed with a per-key IV, so they never repeat.
- **Key update** messages ratchet the application keys forward during long connections.

The project's `secure-channel.js` is a miniature of this design: signed ephemeral keys, a transcript fed into HKDF, one key per direction, and counter nonces.

## 0-RTT, and its catch

With a pre-shared key from an earlier session, a client can send **early data** in its first flight. But 0-RTT data **can be replayed** by an attacker, and it lacks forward secrecy with respect to the PSK. Servers should accept 0-RTT only for idempotent requests (such as a GET with no side effects).

## Hybrid post-quantum key exchange

Since 2024, major browsers and CDNs negotiate **X25519MLKEM768** by default. The shared secret combines X25519 with ML-KEM-768, so the session is secure if **either** algorithm holds. `check-tls.js` from the Internet Security course shows it:

```
protocol:        TLSv1.3
key exchange:    X25519MLKEM768
```

That protects today's traffic against "harvest now, decrypt later" attackers who record it and wait for a quantum computer (chapter 6).
