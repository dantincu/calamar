# Public-key infrastructure and certificates

Diffie-Hellman needs authentication, and signatures need you to know **whose** public key you hold. A **public-key infrastructure** (PKI) answers "is this really bank.example's key?"

## X.509 certificates

A certificate binds an identity to a public key, signed by an issuer:

| Field | Example |
|---|---|
| Subject / Subject Alternative Names | `CN=example.com`, `DNS:example.com, DNS:*.example.com` |
| Subject public key | an ECDSA P-256 key |
| Issuer | `Cloudflare TLS Issuing ECC CA 3` |
| Validity | not before / not after |
| Extensions | key usage, `CA:FALSE`, the CRL and OCSP locations, embedded SCTs (Certificate Transparency) |
| Signature | the issuer's signature over all of the above |

## The chain of trust

Browsers and operating systems ship a set of **root CAs**. Roots sign **intermediate** CAs (keeping the root keys offline), and intermediates sign server certificates. `check-tls.js` walks the chain that example.com sends:

```
0: example.com                       (issued by Cloudflare TLS Issuing ECC CA 3)
1: Cloudflare TLS Issuing ECC CA 3   (issued by SSL.com TLS Transit ECC CA R2)
2: SSL.com TLS Transit ECC CA R2     (issued by SSL.com TLS ECC Root CA 2022)
```

Validation checks each signature up to a trusted root, plus the names, validity periods, key usages and path constraints. Bugs in validation code (accepting a non-CA certificate as an issuer, mishandling names) have repeatedly caused serious vulnerabilities. Use the platform's validator; never write your own.

## The weak point: any CA can issue for any domain

There are about 150 trusted roots, and any of them (or their intermediates) can technically issue a certificate for any name. Compromised or careless CAs have done exactly that: DigiNotar in 2011 (fraudulent `*.google.com` certificates, used to spy on users in Iran), and others. Defenses:

- **Certificate Transparency** (RFC 6962/9162): every publicly trusted certificate must be logged in public, append-only **Merkle-tree logs**, and browsers require proof of logging (SCTs). Domain owners can watch the logs (crt.sh) for certificates they didn't request. Misissuance becomes detectable.
- **CAA DNS records** say which CAs may issue for your domain: `example.com. CAA 0 issue "letsencrypt.org"`.
- **Root program policies**: browsers distrust CAs that misbehave.

### Merkle trees in one formula

A Merkle tree hashes leaves pairwise up to a single root: $h_{\text{parent}} = H(0\text{x}01 \,\|\, h_{\text{left}} \,\|\, h_{\text{right}})$, with leaves $H(0\text{x}00 \,\|\, \text{entry})$. (The different prefixes stop leaves and inner nodes from being confused.) Proving that an entry is in a log of $N$ entries takes only $\lceil \log_2 N \rceil$ hashes. For a billion certificates, that's 30 hashes.

## Revocation, and why it's hard

When a key is compromised, its certificate must be **revoked** before it expires:

- **CRLs**: lists of revoked serial numbers, often large and slow to update.
- **OCSP**: ask the CA about one certificate. It leaks browsing to the CA, and browsers "soft-fail" when the CA doesn't answer, which an attacker can simply block. Let's Encrypt shut down its OCSP service in 2025, in favor of CRLs.
- **Short-lived certificates** are the practical answer: certificate lifetimes are shrinking (90 days at Let's Encrypt; the CA/Browser Forum has voted to bring the maximum down to 47 days by 2029). A stolen key is useful only briefly. This only works with automated issuance, which is why ACME matters.

## Beyond the web PKI

- **Pinning**: an app trusts only a specific key or CA for its own backend. It's strong, but risky: a key change without an app update locks out users. Prefer pinning to a CA, or pinning a set of backup keys.
- **SSH** uses trust on first use (`known_hosts`), or SSH certificates signed by your own CA.
- **Private PKIs** issue certificates to internal services and devices. Mutual TLS (mTLS) authenticates both sides, as in many service meshes.
- **Signal and similar apps** let users compare safety numbers: fingerprints of identity keys, checked in person. That's the same idea as the identity keys in the project.
