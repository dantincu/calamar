# Message authentication codes

A **MAC** proves that a message comes from someone who knows the key, and wasn't altered:

$$
t = \operatorname{MAC}_K(m), \qquad \text{verify: } \operatorname{MAC}_K(m') \stackrel{?}{=} t'
$$

The security goal is **unforgeability**: even after seeing tags for many messages of their choice, an attacker can't produce a valid tag for a new message.

Unlike signatures, MACs are symmetric: anyone who can verify can also create tags. So they authenticate between parties that share a key, and provide no non-repudiation.

## The naive construction fails

$\operatorname{MAC}_K(m) = H(K \,\|\, m)$ looks reasonable. With SHA-256 it's broken by **length extension**: from $t = H(K \,\|\, m)$, an attacker computes a valid tag for $m \,\|\, \text{pad} \,\|\, \text{"&admin=true"}$ without knowing $K$, because SHA-256's output *is* its internal state after processing $K \,\|\, m \,\|\, \text{pad}$. This broke real APIs (Flickr, 2009).

## HMAC

HMAC (RFC 2104) nests two hash calls with two derived keys:

$$
\operatorname{HMAC}(K, m) = H\Big((K' \oplus \text{opad}) \,\Big\|\, H\big((K' \oplus \text{ipad}) \,\|\, m\big)\Big)
$$

- $K'$ is the key padded with zeros to the hash's block size (64 bytes for SHA-256), or first hashed if longer;
- $\text{ipad}$ is the byte `0x36` repeated, and $\text{opad}$ the byte `0x5c` repeated.

The outer hash seals the inner one, so length extension doesn't work. HMAC is provably a secure MAC under mild assumptions about the compression function. It even stayed secure with MD5 and SHA-1 for years after collisions were found in them (though you shouldn't rely on that).

From `hashes.js`:

```
HMAC-SHA256 tag: 220aff60f6…
  genuine message verifies? true
  amount=900 with the same tag? false
```

## Verify in constant time

```js
crypto.timingSafeEqual(given, expected)   // not: given === expected
```

A normal comparison stops at the first differing byte. By measuring response times, an attacker can find the correct tag **one byte at a time**: at most $256 \times 32$ attempts for a 32-byte tag, instead of $2^{256}$. Constant-time comparison closes this side channel. (Remote timing attacks of this kind have been demonstrated in practice against real software.)

## Other MACs

| MAC | Notes |
|---|---|
| **HMAC-SHA256** | the default for APIs, webhooks, JWT (HS256), cookies |
| **Poly1305**, **GHASH** | one-time polynomial MACs inside ChaCha20-Poly1305 and AES-GCM; never reuse their keys |
| **KMAC** | the SHA-3-based MAC |
| **CMAC** | a block-cipher-based MAC (AES-CMAC) |

## Encrypt-then-MAC

When combining a cipher and a MAC by hand (in legacy designs), **MAC the ciphertext** (and the IV and headers), and check the MAC *before* decrypting. MAC-then-encrypt, as in old TLS, led to the padding oracle attacks of the previous chapter. Better still, use an AEAD, which gets this right for you.
