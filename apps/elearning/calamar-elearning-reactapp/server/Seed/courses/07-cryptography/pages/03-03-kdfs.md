# Key derivation: HKDF and password hashing

Keys must be **uniformly random**. Two very different situations produce secrets that aren't, and each has its own tool.

## From a high-entropy secret: HKDF

A Diffie-Hellman shared secret has plenty of entropy, but it isn't uniform (it's a group element with structure), and you usually need several independent keys from it. **HKDF** (RFC 5869) works in two steps.

**Extract** concentrates the entropy into a pseudorandom key:

$$
\text{PRK} = \operatorname{HMAC}(\text{salt},\ \text{IKM})
$$

**Expand** stretches it into as many output bytes as needed, bound to a context string $\text{info}$:

$$
T(0) = \varepsilon, \qquad T(i) = \operatorname{HMAC}\big(\text{PRK},\ T(i-1) \,\|\, \text{info} \,\|\, i\big), \qquad \text{OKM} = T(1) \,\|\, T(2) \,\|\, \cdots
$$

- **IKM** is the input keying material (the DH output); the **salt** is optional and non-secret, and can be a transcript hash;
- different `info` strings ("client key", "server key", "v1 encryption") give **independent** keys from the same secret.

The project's `secure-channel.js` derives one key per direction this way:

```js
const okm = crypto.hkdfSync('sha256', shared, transcript, 'secure-channel demo v1', 64);
```

TLS 1.3's whole key schedule (chapter 5) is a chain of HKDF steps.

## From a low-entropy secret: password hashing

Passwords have little entropy (often under 40 bits), so the defense is to make each guess **expensive**. A password hashing function, or password-based KDF, is deliberately slow, and ideally **memory-hard**:

| Function | Cost parameters | Notes |
|---|---|---|
| **Argon2id** | memory $m$, iterations $t$, parallelism $p$ | winner of the Password Hashing Competition (2015); the first choice |
| **scrypt** | $N$ (CPU/memory), $r$, $p$ | memory use $\approx 128 \cdot N \cdot r$ bytes |
| **bcrypt** | cost $c$: $2^c$ iterations | not memory-hard; 72-byte input limit |
| **PBKDF2** | iterations | not memory-hard; for FIPS environments; 600,000+ iterations with SHA-256 |

**Why memory-hardness?** An attacker's advantage comes from parallel hardware: GPUs and ASICs have thousands of cores, but little fast memory per core. If each guess needs 64 MiB of RAM that's accessed in a data-dependent order, the number of parallel guesses is bounded by memory, not by cores. With scrypt at $N = 2^{17}$ and $r = 8$, each guess needs $128 \times 2^{17} \times 8 = 2^{27}$ bytes, or 128 MiB.

**Cost tuning**: pick the slowest parameters your servers can afford at peak login rate. Something like 100–500 ms per hash on one core is typical. Store the parameters with each hash so you can raise them later.

## Never mix them up

- HKDF on a password: fast, so it's brute-forceable. **Wrong.**
- Argon2 on a DH secret: wasted time. Not insecure, just pointless.
- A password used directly as an AES key: **wrong**. Derive the key with Argon2id or scrypt and a random salt, as password managers and disk encryption do.

## Randomness

Every key, nonce, salt and IV ultimately comes from a **cryptographically secure random number generator**: `crypto.randomBytes`, `getrandom()`, `/dev/urandom`, `RandomNumberGenerator`. Never use `Math.random()` or similar general-purpose generators. Their outputs are predictable from a few samples. Broken randomness has broken real systems: the Debian OpenSSL bug (2008) left only 32,768 possible keys, and a flawed random number generator in Android's Java libraries let attackers steal Bitcoin in 2013 (through repeated ECDSA nonces, chapter 4).
