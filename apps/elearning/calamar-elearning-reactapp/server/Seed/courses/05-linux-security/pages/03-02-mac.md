# Mandatory access control: AppArmor and SELinux

Ordinary permissions are **discretionary**: owners decide, and root bypasses them. **Mandatory access control (MAC)** adds a policy, loaded into the kernel, that even root processes can't override. A compromised web server confined by MAC can't read `/etc/shadow`, start a shell or write outside its directories, even if it runs as root.

| | AppArmor | SELinux |
|---|---|---|
| Default on | Debian, Ubuntu, SUSE | RHEL, Fedora, Rocky, Alma |
| Model | per-program profiles of **paths** | **labels** (contexts) on every file and process, plus type-enforcement rules |
| Learning curve | gentle | steep, but very powerful |

## AppArmor

A profile lists what a program may do; everything else is denied. The attached `usr.local.bin.myapp`:

```
profile myapp /usr/local/bin/myapp {
  include <abstractions/base>
  network inet stream,
  /etc/myapp/** r,
  /var/lib/myapp/** rwk,
  /var/log/myapp/*.log a,       # append only: it can't erase its own logs
  deny /etc/shadow r,
}
```

Developing a profile:

```bash
$ sudo apparmor_parser -r /etc/apparmor.d/usr.local.bin.myapp   # load it
$ sudo aa-complain /usr/local/bin/myapp     # log, don't block
#   ...exercise the app: every feature, every error path...
$ sudo aa-logprof                           # review the logged accesses, add rules
$ sudo aa-enforce /usr/local/bin/myapp      # block
$ sudo aa-status
```

Permissions: `r` read, `w` write, `a` append, `k` lock, `m` map as executable, `x` execute (`ix` inherit this profile, `px` switch to the target's profile, `ux` unconfined, which should be avoided).

## SELinux

Every file and process has a **context** `user:role:type:level`. The rules are mainly about **types**: the process type `httpd_t` may read files of type `httpd_sys_content_t`, and nothing else.

```bash
$ getenforce                         # Enforcing, Permissive or Disabled
$ ls -Z /var/www/html                # file contexts
$ ps -eZ | grep httpd                # process contexts
```

The classic problem: you move a site to `/srv/site`, and Apache gets "Permission denied" despite `chmod 755`, because the files have the wrong **label**:

```bash
$ sudo semanage fcontext -a -t httpd_sys_content_t "/srv/site(/.*)?"   # record the rule
$ sudo restorecon -Rv /srv/site                                       # apply the labels
```

Optional behaviors are **booleans**:

```bash
$ getsebool -a | grep httpd
$ sudo setsebool -P httpd_can_network_connect on    # let the web server open outgoing connections
```

Finding out why something was denied:

```bash
$ sudo ausearch -m AVC -ts recent | audit2why
```

## Don't turn it off

The most common "fix" for SELinux problems on the internet is `setenforce 0`, followed by disabling it permanently. That removes one of the strongest layers you have. Instead, set **one domain** to permissive while you work out its rules:

```bash
$ sudo semanage permissive -a httpd_t     # only the web server's domain is permissive
```

Fix the labels or booleans, then remove the exception.
