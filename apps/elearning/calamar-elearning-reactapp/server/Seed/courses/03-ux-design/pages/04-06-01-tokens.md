# Design tokens

A **design token** is a named design decision: `--color-text-muted` instead of `#5f6168`. Tokens come in tiers:

| Tier | Example | Who uses it |
|---|---|---|
| **Primitive** | `--neutral-700: #5f6168` | only the semantic tier |
| **Semantic** | `--color-text-muted: var(--neutral-700)` | components |
| Component (optional) | `--button-primary-bg: var(--color-primary)` | one component |

Components never use primitives. When the design changes ("muted text should be darker"), you change one semantic token, and every component follows. The same goes for dark mode: redefine the semantic tokens and nothing else.

## Name tokens by role, not by appearance

- Good: `--color-danger`, `--color-surface`, `--color-on-primary`
- Bad: `--color-red`, `--color-light-gray`, `--color-white-text`

`--color-on-primary` means "content drawn *on* the primary color". It's white in the light theme and dark in the dark theme, which a name like `--color-white-text` couldn't survive.

## The semantic tokens of this course

```css
:root, [data-theme="light"] {
  --color-bg: var(--neutral-50);            /* page */
  --color-surface: #ffffff;                 /* cards, inputs, dialogs */
  --color-border: var(--neutral-200);       /* decorative */
  --color-border-strong: var(--neutral-500);/* input borders: 3:1 */
  --color-text: var(--neutral-900);
  --color-text-muted: var(--neutral-700);
  --color-primary: var(--brand-600);
  --color-primary-hover: var(--brand-700);
  --color-primary-active: var(--brand-800);
  --color-on-primary: #ffffff;
  --color-focus-ring: var(--brand-500);
  --color-link: var(--brand-700);
  /* … plus success, warning, danger and info: -, -soft and on-…-soft */
}
```

## Tokens make promises; check them

Each token pair that appears together is a promise: "muted text is readable on the page background". `build-palette.js` lists those pairs with a minimum ratio, and `--report` checks every one:

```
light
  ok   10.94 >= 4.5  color-text on color-bg
  ok    5.88 >= 4.5  color-text-muted on color-bg
  ok    4.60 >= 4.5  color-on-primary on color-primary
  ok    3.30 >= 3    color-border-strong on color-surface
  …
all pairs pass
```

**The report earns its keep.** The first version of this palette used `neutral-600` for muted text. It passes on white (4.6:1), but the page background is `neutral-50`, and the quotient rule gives $4.6 / 1.05 = 4.38$, below 4.5. The report flagged it, and the token moved to `neutral-700` ($6.2 / 1.05 = 5.9$). Without the check, muted text on the page background would have failed WCAG while passing on every card.

## Generating the CSS

```bash
node build-palette.js > palette.css
```

`palette.css` (attached) holds the primitives, each annotated with its OKLCH value and contrast on white, and the semantic tokens for light and dark (next lesson). Run the script in your build, and the palette can't drift from its rules.
