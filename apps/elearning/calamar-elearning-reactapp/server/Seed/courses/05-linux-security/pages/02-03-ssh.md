# Hardening SSH

An SSH server on the internet receives login attempts within minutes of going online, all day long. The goal: **keys only, no root, few features, and automatic bans for scanners**.

## Why keys beat passwords: the numbers

An attacker guessing online is limited by the network and by `MaxAuthTries`, but botnets have many addresses and infinite patience. A human-chosen password might come from a space of $N \approx 10^{9}$ realistic candidates, or far fewer if it's in a leaked list. An Ed25519 key offers about $2^{128} \approx 3.4 \times 10^{38}$ work for an attacker. Even at a billion guesses per second, the expected time is

$$
\frac{2^{128}}{2 \times 10^{9}\ \text{s}^{-1}} \approx 1.7 \times 10^{29}\ \text{s} \approx 5 \times 10^{21}\ \text{years}
$$

A key can't be guessed, phished out of a password manager, or reused on another site. It can be stolen from a laptop, though, so protect it with a passphrase (and `ssh-agent`), or keep it on a hardware key (`ssh-keygen -t ed25519-sk`).

## The configuration

The attached `10-hardening.conf` goes in `/etc/ssh/sshd_config.d/`:

| Setting | Why |
|---|---|
| `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `AuthenticationMethods publickey` | keys only |
| `PermitRootLogin no` | log in as yourself, then `sudo`: accountability, and root is the first name every bot tries |
| `AllowGroups ssh-users` | an allow-list: new or system accounts can't log in by accident |
| `MaxAuthTries 3`, `LoginGraceTime 30` | slow down guessing; drop idle half-open connections |
| `X11Forwarding no`, `AllowAgentForwarding no`, `AllowTcpForwarding no` | features that let a login become a pivot into other networks |
| `LogLevel VERBOSE` | logs the fingerprint of the key used for each login |

**sshd uses the first value it reads** for most keywords. The main `sshd_config` includes `sshd_config.d/*.conf` near its top, so this drop-in wins over the settings further down. Always check the *effective* values:

```bash
$ sudo sshd -t                                   # syntax
$ sudo sshd -T | grep -Ei 'permitroot|passwordauth|authenticationmethods'
```

## The safe procedure

1. Install your public key, and confirm that you can log in **with the key** (`ssh -o PasswordAuthentication=no server`).
2. Add yourself to `ssh-users`.
3. Install the drop-in, run `sshd -t`, and `systemctl reload ssh` (or `sshd`).
4. **Keep your current session open** and test a new login in another terminal. Only then log out.

## fail2ban

fail2ban reads the logs, and bans addresses with too many failures in the firewall. The attached `jail.local`:

```ini
maxretry = 5
findtime = 10m
bantime  = 1h
bantime.increment = true     # 1h, 2h, 4h... for repeat offenders
```

With these values, one address can make at most 5 failed attempts per ban cycle. Instead of thousands of guesses per hour, it gets at most about 5 per hour, and fewer and fewer as `bantime.increment` doubles the ban each time. It's not a substitute for keys only, but it cuts the log noise and the load.

```bash
$ sudo fail2ban-client status sshd
$ sudo fail2ban-client set sshd unbanip 203.0.113.7
```

Put your own office or VPN range in `ignoreip`, so that a few typos can't lock you out.

## Even better: don't expose SSH

- Allow port 22 only from known addresses in the firewall (next chapters).
- Or reach servers through a **bastion host** (`ssh -J bastion server`) or a VPN such as WireGuard, so that SSH isn't on the internet at all.
- For larger fleets, **SSH certificates** (`ssh-keygen -s ca_key …`) replace the `authorized_keys` sprawl with short-lived, centrally issued credentials.

## Audit the keys

```bash
$ sudo find /home /root -name authorized_keys -exec ls -l {} \; -exec cat {} \;
```

Every key should belong to a person you can name. Old keys of people who have left are a classic way in.
